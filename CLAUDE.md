# cases

CLI and local web inbox for a store of cases raised by an agent and answered by a human. The store is one SQLite file: a row per case and a row per event, the event's JSON record as written, numbered within its case. Each event keeps the name it had as a file (`NNNN-<author>-<event>.json`) in `Event.File`. State is the fold of a case's events in number order. The runtime is the Go standard library plus kong, goldmark, go-toml and modernc.org/sqlite (pure Go, no cgo).

## Workflow

- Personal repo at github.com/ryanlewis/cases (public). Commit to `main` and push; CI runs on push and pull requests.
- **DO** use Conventional Commits.
- **NEVER** edit or delete events in a store, by hand or with `sqlite3`. Changes to the record format must keep reading records written by earlier versions; a schema change raises `schemaVersion` in `internal/store/sqlite.go`, and a store with a higher version is refused.
- **DO** update `modernc.org/libc` together with `modernc.org/sqlite`: the driver only works with the libc version its own go.mod pins.
- **DO** update README.md in the same change when a command, flag, event or record field changes.
- **DO** update `internal/skill/SKILL.md` when adding, removing or changing a subcommand's surface. The bundled agent skill ships in the binary and drifts silently otherwise.

## Architecture

- `internal/store/` — the store.
  - `types.go` — kinds, urgencies, states, authors, event types, and one record struct per event.
  - `fold.go` — `foldRows` folds a case's event rows into a `Case`, filling `Event.File` with the event's file name. `apply` is the only place transitions are checked; the record validators it calls live in `validate.go`.
  - `sqlite.go` — `DB`, the store in one SQLite file, and its schema: `cases`, `events` (`change` INTEGER PRIMARY KEY AUTOINCREMENT, `case_id`, `seq`, `author`, `event`, `at`, `data`, unique `(case_id, seq)`), `archive_cases`, `archive_events` and `meta(schema_version)`. The pool opens lazily with WAL, `synchronous=FULL`, `fullfsync`, foreign keys, a 5s busy timeout and `_txlock=immediate`. `open` stats the path before every read and write, records a pool only when the file is the same before and after the pool connects, and opens a new pool when the file was removed or replaced. It returns a `release` func: it counts the calls using each pool, and every caller (`List`, `IDs`, `Get`, `Poll`, `write`) defers `release`, so a pool for a replaced file closes at once when unused, or when its last call is done; reads of a missing or empty file are `fs.ErrNotExist` and create nothing, and only `Create` makes the file. Creating refuses while a `-wal` or `-shm` of a removed store is still beside the path (`checkLeftovers`), and retries the WAL switch on SQLITE_BUSY, which SQLite returns without waiting when two writers make the store at once (`useWAL`). `checkVersion` runs in every write and poll transaction, so a running serve or wait stops at a newer schema. `Disconnect` closes the pools (`Close` is the close event); `main` and the test harnesses call it.
  - `write.go` — `Create` and one append method per event. Each write is one immediate transaction: it takes the store's write lock, stamps the record's time, folds the case, checks any `AtRevision(rev)` (a case whose `Revision()`, its number of event rows, has moved on fails with `ErrStale`), runs `apply` on the new event, and inserts it at the case's latest `seq` + 1. Stamping inside the lock keeps event times in stored order. `Create` chooses the id (time plus slug, `-2` on a clash with a live or archived case) and inserts the case row before its open event, in the same transaction. `commit` can be swapped to fail the last step.
  - `store.go` — the `Store` interface the CLI and web read and write through, keyed by case id. `*DB` is the only implementation. `Deps.Cases` and `web.New` take a `Store`; `prune`, `serve`'s instance file and `status` use the path. Tests override one method by embedding the store (`runCasesWith`, `newAppWith`).
  - `list.go` — `List`, `IDs`, `Get` and `Poller`. The poller first reads the highest `change` and the number of cases; when both are unchanged it returns its cache. Otherwise, in one read transaction, it lists the case ids, drops cases no longer there, and folds the cases with an event whose `change` is above the highest it had, plus any id it has not seen (such as a case put back from the archive, whose events keep their old `change`). `cases wait` and `cases serve` use it.
  - `archive.go` — `Archive` (moves a case's rows into the archive tables, refusing an id the archive has with `ErrArchived`) and `Delete`, each one transaction taking `AtRevision`. They are not on `Store`: `cases prune` asserts `Deps.Cases` to its `pruner` interface.
  - `storetest/` — test-only helpers that insert raw event rows (`InsertEvent`) and read the archive (`Archived`). It must not import `store`, because the store's own tests use it.
  - `describe.go` — `(*Case).Describe(ev)`, plain-text lines for an event, shared by `show` and the web thread.
- `internal/web/` — `cases serve`. `web.go` holds the `Server`, routes, the request guard (Host must be the loopback listen address; POSTs with a foreign `Sec-Fetch-Site` or `Origin` get 403; CSP `default-src 'self'`) and the request log. `views.go` holds the handlers and view data, `forms.go` holds form parsing. `events.go` holds the event stream, `GET /events?after=V`: every read through the server (each request, and serve's one-second `pollStore` ticker) records `versionOf(cases)`, a digest of the case ids and revisions, and wakes the open streams when it moves, skipping that and the notifier when the poller hands back the same cases; a stream sends the version whenever it differs from the one the page has (`after`, or `Last-Event-ID` on a reconnect), at most once every `streamGap`. A stream never goes idle, so `cases serve` passes `EndStreams` to `web.Serve`, which calls it as the shutdown starts. `GET /cases/{id}/thread` (`oldThread`) only answers tabs from before pages followed the store. Templates in `templates/` and `static/` are embedded. Reads go through one mutex-guarded `store.Poller`; POSTs load the case from the store with `Store.Get` and write through `Store.Answer`, `Store.Park` or `Store.Resume` in `writeContext(r)`, the request's context without its cancellation, so a browser that goes away mid-post does not drop the answer; then they redirect.
- `internal/instance/` — the file a running `cases serve` records itself in (pid, url, store) for `cases status`: `$XDG_STATE_HOME/cases/serve-<slug>-<hash>.json`, outside the store. `Running` treats a dead pid or an address that refuses connections as no instance.
- `internal/service/` — `cases serve` as a user service: a launchd agent (`~/Library/LaunchAgents/com.github.ryanlewis.cases.serve.plist`, `RunAtLoad`, `KeepAlive`) on macOS, a systemd user unit (`$XDG_CONFIG_HOME/systemd/user/cases-serve.service`, `Restart=always`) on Linux, one per user. A `Manager` (GOOS, Dir, UID and a `Runner` for launchctl or systemctl) renders the file (`Plist`, `Unit`), writes it and loads it (`Install`, which boots out a loaded agent first and retries the bootstrap), removes it (`Uninstall`), and reads back without changing anything (`Installed`, `Active`, and `Args`, which parses the command out of the file). `Default()` is the real one for this machine.
- `internal/skill/` — the bundled agent skill. `SKILL.md` is the neutral source, embedded; one adapter per agent (`claude.go`, `codex.go`, `pi.go`) renders it and knows the agent's skill directory. `cases skill install|uninstall|show|list` in `cmd/cases/skill.go`.
- `internal/config/` — the TOML config file (`$XDG_CONFIG_HOME/cases/config.toml`). `Keys` is the allow-list of settings, each naming the flag it seeds. `Load` returns a `File` that is never nil, so `cases config` can report a broken file. `(*File).Resolver()` is a kong resolver; it yields nothing for a flag whose env var is set, so precedence is flag > env > file > default.
- `cmd/cases/` — kong CLI. One file per subcommand, each with a `_test.go` sibling. `Deps` carries the store's file path, the `Store` (a `*store.DB` that `main` opens and disconnects when the command returns; it must be set), the streams and the loaded config. `Deps.Service` returns the `service.Manager` that `cases service` uses; `main` sets it to `service.Default`, and when it is nil the service commands fail. `cases service` (`service.go`) has a default subcommand, `status`, which reports read-only whether the service is installed, loaded and answering, names any disagreement and exits 1 unless all three hold. `install` bakes the store, config file, `--listen` and `--as` into the service's `cases serve` command, and refuses while a serve runs for the store or the address is taken, except where a loaded service already on that store or address is the serve found there. `uninstall` stops the service and removes its file. The `listen` and `name` config keys seed `service install` as well as `serve`. `sweep` and `prune` pause `writePause` (1ms) after each write so other writers get the store's lock. `main` and `runCases` both load the config off the argv before building the parser, and a config error stops every command except the `config` subcommands (marked by `diagnosesConfig`).

## Conventions

- `apply` checks everything before changing the case, so a refused event leaves it unchanged. The fold skips a refused or malformed event row, naming it by its file name in `Case.Problems`; it fails only when there is no valid open event.
- The writer and the reader use the same `apply`, so anything the CLI writes will fold.
- Timestamps are UTC, set by the store when the record leaves them zero.
- `Event.Data` holds the record's bytes as written (the `data` column), so unknown fields survive and appear in `show --json`.
- Never open a store file in-process with `os.Open` and close it: closing any descriptor on the database file drops the SQLite locks the process holds on it. `os.Stat` is fine.
- `[]string` flags whose values can contain commas need `sep:"none"`.
- htmx is vendored at `internal/web/static/htmx.min.js` and embedded. Never load it from a CDN. To upgrade: take `dist/htmx.min.js` from the npm tarball, check the tarball against the registry's integrity hash, and update the version, integrity and `htmxSHA256` in `views.go` (`TestStaticHTMXIsTheRecordedRelease` checks the file).
- Web pages have no inline scripts or styles, so the CSP holds. The only script files are the vendored htmx and our own `internal/web/static/prefs.js`, which applies the browser-stored preferences (`data-theme`, `data-face`, `data-size`, `data-links`, `data-notify` on `<html>`) before first paint and, when desktop notifications are on and the browser allows them, polls `GET /notifications?after=N` every 5s and shows what `internal/notify` queued, keeping its cursor in localStorage; add an option by extending its `OPTIONS` table, the CSS keyed on the attribute, and a fieldset in the options dialog in `layout.html` (there is no `/options` page; the overlay is a native `<dialog>` opened by `prefs.js`). On a page whose `<body>` has `data-events`, `prefs.js` also opens that event stream while the tab is shown (six streams would use every connection a browser allows one address), passes each version to the other tabs over a `BroadcastChannel`, fires `store-changed` on the body for each new one, and drops the page's htmx requests for 10s after a form is sent; and it puts back the focus and caret of a field that `hx-preserve` moved. Page changes use CSS view transitions: `view-transition-name`s (`masthead`, `inbox-list`) go only on elements that persist across pages and must stay unique on a page, and `prefers-reduced-motion` turns them off. Everything is escaped by `html/template`. The only `template.HTML` is goldmark output, with raw HTML left off (never `html.WithUnsafe`).
- Answers from the web go through the same store functions as the CLI. Do not add another way to write events. A web form that writes carries the case's `Revision()` in a hidden `revision` field, and its handler passes it back with `store.AtRevision`, so a form from a page older than the case gets 409 and writes nothing. Pages follow the store through their event stream: each region refreshes on `store-changed` (the inbox list and the case view also ask every 60s), swapping with `settle:0ms` so the new element listens at once, and `/done` does not follow it. The case view (`#case`, `GET /cases/{id}/view?state=S&revision=R&form=F`) sends the page to a fresh GET when the state has changed, answers 204 at revision R, and otherwise draws the whole view again with the form at the case's revision, or still at F after an amend that changed the question (`AmendSeq` above F), so that send is refused once. Its fields carry ids and `hx-preserve` (`fieldID`, `choiceID`), as does the refusal line (`#refusal`, hidden when empty), so a refresh keeps what the human typed and chose; reloading instead would throw it away. The 409 still stops a send that races a change. Web tests send it with `withRevision(form, rev)` or read it off a page with `pageRevision`.
- `cases wait` wakes on a new human answer, park or resume. New means the event (case id and file name) was not there on its first poll, or is later than `--since`. It exits 2 on timeout (`exitTimeout`).

## Testing

- Fold tests build events in memory with `fold(t, steps...)` in `internal/store/fold_test.go`. `TestTransitionMatrix` tries every event from every state against the lifecycle diagram. Add to it when the lifecycle changes.
- Store tests use a database in `t.TempDir()`: `newDB(t)` or `openDB(t, path)`, disconnected at cleanup. `fixClock` pins the event clock; `failCommit` makes the commit fail. `insertRow` stores an event row with no checks (through `storetest`), and `storedRows` and `archivedRows` read the rows back. `TestTwoWritersOnOneFileSerialise` and `TestTwoProcessesOnOneFileSerialise` (which re-runs the test binary as two writer processes) check that concurrent appends number events 1 to n with no gap or duplicate. `TestStoreContract` runs the `Store` interface.
- CLI tests call `runCases(t, stdin, args...)` in `cmd/cases/main_test.go`. It parses with the real kong grammar, opens the store the arguments name for the one command, and captures stdout and stderr. `newStore(t)` is a store path that does not exist yet and `openStore(t, path)` a `*store.DB` disconnected at cleanup; a test that builds `Deps` itself sets `Cases: openStore(t, path)`. Damaged or unknown events are inserted with `storetest.InsertEvent`. `Deps.Poll` is 10ms in tests. `TestMain` points `HOME` and the XDG directories at a scratch directory, so tests never see the developer's config file or default store; `writeConfig(t, body)` in `config_test.go` puts a file at the default location for one test. `runCases` sets no `Deps.Service`, so no test can reach the real launchctl or systemctl; service tests use `runCasesDeps(t, cases, set, stdin, args...)`, whose `set` edits the `Deps` before the command runs, to inject a `Manager` with a recording runner and a `t.TempDir()` directory (`runService` in `service_test.go`). `internal/service` tests use the same kind of fake runner.
- Web tests (`internal/web`) use `newApp(t)` and `a.do(method, path, form, headers)` with `httptest`; `a.db` is the app's store and `a.eventFiles(t, id)` names a case's events. Requests carry `Host: 127.0.0.1:8765` unless the test sets another. Stream tests serve on a real listener with `serveApp`, which ends the streams before the server closes, and read a stream with `openStream`; `a.server.Poll()` stands in for serve's ticker.
- `e2e_test.go` runs a decision case through open, answer, wait, pickup and close.
